# The media library — uploading images from /admin

Until now every picture on this site was a file a developer committed under
`assets/`. That is still true of most of them, and deliberately so. What is
new is that an admin can now add a picture **without a developer and without
a deploy**, and use it in the Page Builder straight away.

This document covers what that is, how to switch it on, and — just as
importantly — what it is not.

---

## Two kinds of image, on purpose

|   | Repository assets | Uploaded CMS media |
|---|---|---|
| **Where the file is** | committed in this repository under `assets/` | the site's own Supabase Storage bucket |
| **How it gets there** | a developer commits it | an admin uploads it in `/admin > Media Library` |
| **Listed by** | `assets/asset-manifest.json` (generated by `tools/build-asset-manifest.js`) | the `media` block of the CMS record |
| **Stored in a page as** | `assets/images/logo.png` | `https://<project>.supabase.co/storage/v1/object/public/cms-media/media/<name>.png` |
| **Validated by** | `CMS.sections.assetPath()` | `CMS.sections.mediaPath()` |
| **Needs a deploy to appear** | yes | no |

The two validators share no code path. `assetPath()` refuses anything that
is not a plain relative path under `assets/images/` or `assets/icons/` — it
refuses an uploaded URL just as firmly as it refuses `https://evil.test/x.png`.
`mediaPath()` refuses anything that is not a file in *this site's own bucket*
with a name this code generated. Widening one cannot widen the other.

`CMS.sections.imageRef()` is the union of the two, and is what the image
fields and the picker are held to. There is no third option.

**Nothing about repository assets changed.** Every image already on the site
goes on working exactly as it did, the manifest system is untouched, and a
site that never switches uploads on behaves precisely as it did before.

---

## Switching it on (once, by a developer)

Uploads are **off** until a storage bucket exists, because there would be
nowhere for an upload to go and a silent failure at the moment someone is
trying to publish is the worst possible time to discover that.

In the Supabase dashboard for the project named in `js/cms-config.js`:

1. **Storage → New bucket**
   - Name: `cms-media`
   - Public: **yes** (these are images on a public website)
   - Optionally set a file size limit of 5 MB and restrict the allowed MIME
     types to `image/png, image/jpeg, image/webp, image/gif`.
2. **Storage → Policies → `cms-media`**, add three policies:
   - `SELECT` for `anon` and `authenticated` — visitors read the images
   - `INSERT` for `authenticated` — only a signed-in admin can upload
   - `DELETE` for `authenticated` — only a signed-in admin can delete

   Do **not** grant `INSERT` or `DELETE` to `anon`.
3. In `js/cms-config.js`, set `window.CMS_MEDIA.enabled = true` and deploy.

No key changes. Uploads are authorised with the **admin's own session token**
— the same one that already writes the brand row when you press Save. There
is no service-role key anywhere in this codebase and there must never be one:
everything in `js/` ships to the browser.

The browser-side size limit is a courtesy that saves a doomed upload. The
bucket's own limit is the control. Set both.

### Until it is switched on

The Media Library panel says so plainly and disables its Upload button, and
the Page Builder's **Uploaded images** tab explains why it is empty. The
**Site images** tab keeps working throughout. Nothing breaks and nothing
pretends to work.

## Uploading an image

`/admin` → **Media Library** → **Upload image**. Pick one or more files.

You will see each file checked, then uploaded, then listed. If a file is
refused you are told which file and why, in a sentence you can act on — the
upload is never silently dropped and a refused file never appears in the
library.

Each card in the library shows a thumbnail, the original file name, the real
pixel dimensions, the file size, an **alt text** box and a **Delete** button.

### What is accepted

PNG, JPEG, WebP and GIF, up to the configured limit (5 MB by default).

### What is refused, and why

| Refused | Why |
|---|---|
| any extension outside the four above | including `.svg` — an SVG is a script host, and no amount of sanitising makes one safe to serve from your own origin |
| a file whose MIME type disagrees with its extension | a file has to be what it claims to be |
| a file whose **first bytes** are not a real file of that type | this is what catches a renamed `.exe`, shell script, HTML page or SVG payload; the extension and the MIME type are both things the uploader controls, the signature is not |
| a file starting with `<?xml`, `<!doctype`, `<html`, `<svg`, `<script` or `%PDF` | a document wearing an image's name |
| a file the browser cannot decode as an image | if it will not open here it will not open for a visitor |
| a file over the size limit | checked before a single byte is sent |
| an empty file, or one with no extension at all | there is no way to tell what it is |

### The file name is thrown away

Whatever the file is called on your computer, the object written to the
bucket is named by this code: the name reduced to lowercase letters, digits
and hyphens, truncated, plus a random suffix, under a fixed `media/` prefix.

So `../../../etc/passwd.png` becomes something like
`media/etc-passwd-k3n8qp.png`, `<script>alert(1)</script>.png` becomes
`media/script-alert-1-script-9fj2mq.png`, and two people uploading
`photo.png` never overwrite each other. Traversal is impossible by
construction rather than by filtering, and the upload is sent with
`x-upsert: false` so it cannot replace an existing object either.

`CMS.remote.uploadMedia()` re-checks the generated name against the single
pattern this CMS ever writes, below the UI — so a bug in the admin still
cannot place an object anywhere else in the bucket.

Your original file name is kept as a label in the library, because that is
how you will recognise the picture.

## Using an uploaded image

In the Page Builder, any **Image**, **Card** or **Feature box** element:
press **Choose image**, switch to the **Uploaded images** tab, pick one, press
**Use this image**. You can also upload from inside that tab without leaving
the builder.

The same picker is used for the SEO **share image** (`og:image`), and an
uploaded image is the right answer there: a share image has to be a URL that
Facebook and X can fetch, which the data URLs in the old Image manager never
were.

Then publish the page as usual. The image is already live — it is in the
bucket the moment the upload succeeds — so publishing only has to make the
page point at it.

---

## The Image manager is a different thing

`/admin > Images` replaces **fixed slots**: the logo, the favicon, the login
background. Those stay where they are, stored in the record as data URLs,
because there are a handful of them and they are part of the brand rather
than part of the content.

The media library is for **content**: an open-ended set of pictures, at real
URLs a crawler can fetch and a browser can cache, that do not have to fit
inside the ~5 MB the whole brand record has to fit in.

---

## Deleting

**Delete** removes the object from the bucket first, and only then removes
the row from the library — so the library never claims to have deleted
something it has not. If the delete fails you are told.

A page still pointing at a deleted image will show a broken image. Nothing
rewrites your pages for you, and the confirmation says so.

---

## Performance

- Thumbnails are lazy and carry their real `width`/`height`, so nothing
  reflows as pictures load.
- Only 24 cards are built at a time; **Show more** adds another 24. A library
  of hundreds does not build hundreds of DOM nodes.
- The library metadata lives in the CMS record that is already fetched once
  per page load. Browsing the library makes **no** extra Supabase requests.
- Uploads are sequential, one file at a time, so a failure can be attributed
  to a file.

## For a new white-label site

Everything is configuration:

- `window.CMS_MEDIA.bucket` — the bucket name
- `window.CMS_MEDIA.maxBytes` — the browser-side size limit
- `window.CMS_MEDIA.enabled` — off until the bucket exists

The public URL prefix is derived from `window.CMS_REMOTE.url`, so a second
brand pointed at a different Supabase project gets a different bucket
automatically and cannot accidentally accept the first brand's URLs.

Nothing in the media code names JSK1, `playzone9`, or any particular domain.
